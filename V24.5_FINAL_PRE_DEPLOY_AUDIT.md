# Base Quest Milestones V24.5 — Final Pre-Deploy Audit

This build is derived directly from `BaseQuestMilestones_V24.4_MOBILE_WALLET_QR_FIXED_FINAL.zip`.

Key hardening changes:

- Verified gameplay now stops immediately when the authorized milestone reaches both its score and play-time threshold; a pending mint cannot be bypassed through Start, Space, Tap, or direct `game.start()`.
- After confirmed mint, the next sequential protocol milestone becomes the only valid next run target.
- Contract default mint cooldown is zero so confirmed milestone progression can continue without an unintended 60-second on-chain block.
- Life 1/2 loss preserves the active run; life 3 triggers the persisted 3-minute gameplay retry lock.
- WalletConnect explicitly requests Bohr Testnet during pairing, requires `eth_sendTransaction`, and keeps the official QR/mobile modal.
- Legacy Base builder-code calldata suffixing was removed from BOT transactions.
- Mobile/injected progression reads fail closed rather than guessing `not minted` and risking a reverting gas transaction.
- Browser Wallet selection prefers the active injected provider instead of arbitrary EIP-6963 announcement order.
- Wallet status no longer reports Bohr as connected when balance/RPC reads fail on a wrong network.
- Disconnect clears the static-page cached wallet identity/progression display.

Contract: V23-compatible ABI and milestone rules, with pre-deploy default `mintCooldown = 0`.

## Final line-by-line hardening pass

Additional pre-deploy fixes in the final V24.5 pass:

- Protocol checkpoint score is now a hard floor; hit/shield penalties cannot roll a wallet below its highest sequential protocol-minted checkpoint.
- Verified-run clearing stops any active client run and removes stale mint locks.
- Account changes cannot carry the previous wallet's cached `mintedMilestones` state into a new address while RPC reads are pending.
- `startRun` recovery is bound to the exact transaction sender even if the user changes accounts while confirmation is pending.
- Mint confirmation is attributed only to the account that actually sent the transaction; changing wallets mid-confirmation cannot credit the new account locally.
- Start/Jump/Mint UI actions are disabled while conflicting wallet/start/mint operations are in flight, closing connection/transaction race paths.
- Milestone cards distinguish `Score Reached` from `Ready to Mint` and `Minted` instead of treating score alone as an unlocked NFT.
- Metadata finalization rejects non-HTTPS public URLs, with HTTP permitted only for explicit loopback preview hosts.
- Deployment documentation now matches the fixed Bohr Testnet network configuration and V24.5 GitHub workflows.

## Final concurrency, persistence and viewport hardening

The last pre-deploy pass also verified and hardened the following edge cases:

- A retry lock written by another browser tab immediately terminates any already-running local game in the current tab, preventing a multi-tab bypass of the 3-minute lock.
- Best-score display/persistence can never fall below the permanent score checkpoint represented by the wallet's highest sequential protocol-minted milestone.
- Canvas resize/orientation changes clamp the player back onto the recalculated floor instead of allowing an out-of-bounds/below-floor player position.
- WalletConnect reuses the provider session account list before falling back to `eth_accounts`, reducing unnecessary dependence on public RPC reads for session identity.
- WalletConnect optional-only pairing now puts `eth_sendTransaction` in `optionalMethods` (where the current ethereum-provider actually builds the optional namespace) and keeps BOT in `optionalChains` at both init and connect time; this fixes a subtle QR/mobile session that could pair successfully but lack transaction permission.
- Injected `accountsChanged` handling guards against stale asynchronous `getSigner()` completion, so a signer from the previous account cannot be attached after a rapid account switch.
- `startRun` receipt recovery is bound to the exact transaction sender, and the client verifies that the confirmed session still belongs to the currently connected account before local gameplay begins.
- Mint confirmations are credited locally only to the address that actually sent the transaction; a wallet switch during confirmation cannot credit the newly selected account.
- Start, Jump, Mint, connect and disconnect paths mutually lock conflicting actions while wallet or transaction operations are pending.

## Last release-candidate hardening

- Transaction receipt waiting is now bound to the exact EIP-1193 provider instance that submitted the transaction, instead of the mutable global wallet provider reference. This prevents an account/chain event from redirecting the local confirmation wait while a transaction is pending.
- GitHub Pages deployment validates a configured `VITE_CONTRACT_ADDRESS` as a non-zero 20-byte EVM address before building.
- Remix deployment documentation now explicitly requires the NFT metadata base URI to end in `/`, matching the contract's direct `baseURI + milestone + .json` construction.
